# 后台工作负载与独立采集设计

## 1. 职责边界

本目录负责 XZ、Table、Array 三个后台工作负载的样本准备、实际执行、正确性验证、独立内存采集和报告生成。前台 Krita 操作由 `前台操作/` 维护；基线与冻结并发由仓库根目录对应目录维护。

## 2. 工作负载

- **XZ：** 使用确定性输入素材执行单线程 XZ 压缩。输入素材由固定种子生成，采集前记录 SHA-256，执行后验证输出。
- **Table：** 生成大规模结构化 CSV 数据，执行读取、计算和分组处理，并对关键统计结果进行校验。
- **Array：** 使用 NumPy 创建三个常驻 `float64` 数组并执行实际数值计算。Large 档为每个数组 90,000,000 个元素，分块大小 1,000,000。

Array 的计算过程采用原地/输出参数计算，避免不必要的全量临时副本。A 原地排序，B=A+B，C=sqrt(B*C+0.125)，聚合采用分块 sum/einsum。种子重放验证在被测 worker 内执行，只使用两个 chunk 大小的 float64 缓冲；检查数组数量、dtype、排序、种子多重集合摘要、逐元素关系、聚合值和有限值。A 的多重集合校验是诊断校验和，不是无碰撞密码学证明。

Array prepare 阶段只生成参数 manifest，不提前分配 NumPy 数组。小型 output.json 保存每数组数据 SHA、聚合结果、内存内验证标记和结果摘要；全部校验通过并清理数组后才原子写出。采集器在 worker 外验证参数绑定、输出完整性及摘要，不把大型数组或验证内存搬到采集器中规避计量。

## 3. 独立采集流程

```text
配置 profiles.json
       |
       v
CLI prepare -> 生成操作素材与 manifest
       |
       v
CLI collect -> 创建独立采集会话
       |
       v
systemd transient service + 单操作 worker
       |
       +--> cgroup 内执行工作负载
       |
       +--> 采集器定期读取 cgroup / 系统指标
       |
       v
操作结束 -> 正确性验证 -> 清理服务
       |
       v
summary.json / report.md / mean.csv / 原始证据
```

每轮操作由独立 systemd service 管理，并使用启动门控记录开始时刻。采集器在服务外读取 cgroup 指标，避免把采集器自身的内存计入工作负载。50 ms 采样记录单调时钟、memory.current、memory.peak、memory.stat、memory.events、swap 及可用的系统/进程指标。未知或缺失字段保留为未知，不补零。

## 4. 报告与有效性

报告按操作和轮次汇总峰值、持续时间、匿名内存采样值、变异系数及 OOM 事件。均值曲线仅在各轮真实采样范围及操作生命周期内插值，不在开始前补零，也不在结束后延长最后值。

触及安全 MemoryMax、发生 OOM、操作退出异常、正确性校验失败、证据缺失或清理失败的轮次不得作为有效测量。独立操作报告不包含四操作真实并发测量；不能用独立峰值之和替代并发峰值。

## 5. 与并发实验的接口边界

本目录提供可独立准备和执行的后台工作负载，以及其参数、素材 manifest 和操作实现。并发实验需要使用同一份工作负载实现及正确的素材路径，但并发启动时间、公共监控、进程/cgroup 调度和三种策略逻辑由以下目录分别维护：

- `基线并发/`
- `冻结并发/`

并发目录不应把策略 runner 或并发任务管理器复制回本目录；本目录也不负责定义三线并发策略。
